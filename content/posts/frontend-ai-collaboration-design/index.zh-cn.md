上篇《[AI 写代码，最缺的不是 Prompt，而是一个能暴露错误的现场](/zh-cn/harness-engineering-ai-frontend/)》讲的是为什么：模型不是不会写，而是没有现场感，不知道自己错了，也没办法及时发现。

这篇讲怎么做。

过去一段时间，我把那套想法落成了一个能跑的系统：一套前端 AI 协作系统。它不是一个更长的提示词，而是一组互相咬合的设计：五层约束管住代码往哪写，一个五阶段状态机管住一件事怎么走完，评测管住什么叫做对了，内核管住长流程别中途失忆。

> **2026-11 修订说明**：这篇文章最初写于 2026 年 10 月，描述的是这套方法的早期形态（八个阶段、每阶段一份 Skill）。此后我把整套系统重写成开源工具 [frontend-harness-cli](https://github.com/XingMXTeam/frontend-harness-cli) 并持续迭代，流程的形态变了：阶段变成了内核状态，Skill 改按产物命名，验收换成了带否决权的评分表。本次修订把机制部分全部换成开源版的现行形态，设计思想、实测数据和踩坑记录保留原样。现在文中讲的每个机制，都能在仓库里找到对应实现。

先给结论，再展开。LangChain 在 Terminal Bench 2.0 上做过一个实验：模型不变，只改外围的 Harness，得分从 52.8% 涨到 66.5%，多了 13.7 个百分点，排名从三十名开外进了前五。

我的感受也类似。模型没有变聪明，是它犯错的空间变小了，发现错的速度变快了。

下面按五层约束、五阶段与三个角色、Skill 怎么组织、评测怎么做、内核怎么跑、踩过的坑、怎么落地、它的边界在哪，这个顺序讲。

## 一、五层约束：先把轨道铺好

我把前端的约束分成五层。自下而上是：语言、样式、状态、工程、美学。

每一层回答一个问题。语言层问错不错，样式层问稳不稳，状态层问准不准，工程层问通不通，美学层问对不对。顺序不能乱。代码都编译不过，谈视觉还原没有意义。

**第一层，语言约束。** 用 TypeScript 的严格模式钉死：显式类型，不许用 `any` 绕过去，不许用忽略类型的注释把报错盖住。类型即文档，函数签名要让调用方一眼看出会返回什么、可能出什么问题。

我把这层比作有刻度的尺子。写错了，尺子当场拦住，不需要等运行起来才发现。

**第二层，样式约束。** 颜色、间距、字号全部走设计变量（Design Token），不写死数值；组件样式用 CSS Modules 做作用域隔离。这些规则不靠评审时口头提醒，而是写进 Stylelint 和 ESLint，违反就报红。

这层像一个只有 8 种颜色的调色板。AI 选不了错的颜色，因为错的颜色根本不在板子上。

**第三层，状态约束。** 状态要有显式的结构定义：字段、类型、初始值、哪些可缺省，都写清楚。客户端状态和服务端数据分开，单一数据源。本地存储的键必须带命名空间，能一眼看出它属于哪个页面、哪类数据，而不是随手起个名字全站共用。

这层像一座城市只有一条公路从水厂到每家每户。你不需要猜水从哪来，打开龙头就有，出了问题也知道沿哪条路查。

**第四层，工程约束。** 目录结构、模块之间能不能互相引用，用架构 Lint 强制；文件大小和函数长度设上限——比如单个源文件不超过 300 行，函数也要控制在可读的长度内，超了就必须拆。再加上提交前钩子和 CI，把类型检查、Lint、构建、测试串成一条流水线，不通过就不让进。

这层是交通规则加红绿灯。不是建议你别闯，而是路口的设计让你闯不过去。

**第五层，美学约束。** 设计变量再往上走一层：颜色、间距、圆角、阴影、动效都沉淀成 Token，高频界面模式封装成组件，再用截图对比做视觉回归。

这层像乐高。错误尺寸的积木根本不存在，能拼错的余地就小了。

这里有个前端特有的判断，值得单独说。

LangChain 总结的通用 Harness 是六层：文件系统、沙箱、代码执行、记忆、上下文管理、编排。落到前端，我把前几样做了压缩：文件系统、沙箱、代码执行，本质上都被工程约束吸收了——构建失败就是沙箱失败，Lint 跑通就说明代码能执行；记忆在前端就是状态，归到状态层；编排单独拿出去，变成后面的状态机。

压完之后空出来一层，我把它留给了美学。

这不是凑数。通用 Harness 的文献很少谈美学，因为多数任务的对错是二值的。但前端不一样。Omni-I2C 这类图文转代码基准里，当前最强的模型视觉还原能到七成多，细到参数级的精度只有四成左右，而且实体和布局错误占了所有错误的六成以上（来源：Omni-I2C 基准，2026）。也就是说，功能对了，页面仍然可能是不对的。用户会不会用，很大程度取决于这一层。

这五层在开源版里落在两个地方：一是 `harness init` 时按技术栈装进项目的规则与栈包（Next.js、React、Vue、Node 各一份），二是评测里的五维扫描逐项回查——约束写下去，还要有人查，这两件事缺一不可。下一节先讲流程怎么走。

## 二、五阶段与三个角色：流程是状态机，不是文档

有了轨道，还需要列车时刻表。早期版本我把一个需求拆成八个阶段，每个阶段写一份 Skill 让模型照着走。重写成开源版时，我把这件事推翻了：**阶段不该是文档，应该是代码里的状态。** 文档靠模型"记得遵守"，状态靠程序强制执行——这是整套系统最重要的一次形态变化。

现在一个功能（feature）的一生只有五个阶段，由内核的状态机驱动：

**澄清（clarify）→ 实现（implement）→ 评测（evaluate）→ 确认（verify）→ 交付（done）**，外加一个随时可能进入的**暂停（paused）**。

干活的不是"主对话里的模型"，而是三个角色，各有自己的上下文、输入包和权限边界：

- **规划者（planner）**：只在澄清阶段出现。把一句话需求追问到开放问题清零，然后按固定顺序产出契约文件：`prd.md`（每条需求带编号）、`vision.md`、`tech-design.md`、`pages.json`、`tasks.json`、`rubric.json`、`e2e-cases.json`。你已经有成稿 PRD 也可以：`harness new <功能> --prd <文件>` 直接原文导入，编号一个不改，澄清缩减为只确认加补缺口。
- **开发者（developer）**：在实现阶段一次做一个任务：实现、跑检查、做一次精确提交。它有一个刻意的权限设计——**永远看不到 rubric**。它按计划干活，不是对着考题干活。
- **评判者（evaluator）**：在评测和确认阶段各出现一次，而且两次必须是**不同的全新上下文**。按 rubric 逐条打分，只交证据，不许顺手改代码。

整条流水线有三个原则，都是踩出来的。

**原则一：先定义"完成"长什么样，再写代码。**

澄清阶段结束有一道覆盖门禁（coverage gate）：每条需求编号都必须有至少一条"必查项"（essential）、一条挂在具体锚点上的品质条目（或一份书面豁免）、以及覆盖六大类的端到端用例。覆盖不全，状态机不放行，代码一行都不许写。

为什么这么狠？Anthropic 有个发现我很认同：评分标准的措辞不只是用来判断好坏，它会直接塑造生成者的输出方向。你把"完成"写清楚，AI 写的时候就在朝那个方向收敛。反例就是那句最常见的"把首页做完"——AI 自由发挥六个小时，你验收时发现方向错了。模糊的指令不会被执行，只会被放大。

**原则二：检测和修复必须分开。**

评测只报告问题，永远不许顺手改代码。修复只能回到实现阶段，而且只许修评测报告里列出的开放项。

原因很实际。修复必然引入新问题：评测顺手修了样式，可能改坏类型；修了类型，可能漏掉文案。更麻烦的是评测一旦动了代码，这次评测就没法复现了——你分不清报告说的是哪一版代码。分开之后，每次评测对应一份固定的报告，每次失败走哪条路重试，都有记录可查。

**原则三：否决权大于总分，稳定大于一次通过。**

rubric 里的条目分三档：command（命令真跑）、judge（凭证据判断）、manual。其中两类条目带否决权：**essential 条目得 0 分，整个功能直接判失败；pitfall 条目被触发（比如用了忽略类型的注释绕过检查），同样直接失败——总分再高也没用。**

过了评测还不算完。确认阶段换一位全新的评判者，把所有 judge 条目的证据**从零重新生成**——比上一次评测旧的证据直接记 0 分——并且要求连续通过若干轮。一次通过可能是运气，换人、换证据、连过几轮，才叫稳定。

还有一条和任务绑定的硬校验：开发者声称某个任务做完了，必须报出那次提交的 SHA，内核用 `git rev-parse` 验它真实存在。报一个不存在的 SHA，任务不记完成。这条规则听起来好笑，但它拦下的是真实发生过的事：模型会"声称"自己提交了。

给老读者一张对照表，我早期文章里的八个阶段如今在哪：初始化变成了 `harness init` 命令；文档沉淀消失了——契约文件在澄清阶段就已落盘，产物即文档，交付后由 sync-overview 把稳定结论沉淀进项目概览；发布变成了交付阶段的门禁（你项目自己的构建、测试、Lint 必须全绿）；进化拆成了两条受守护的回路，第五节细说；修复回路住在评测与实现之间。阶段没有消失，只是从"要背的流程"变成了"不用背的状态"。

## 三、Skill 按产物命名：阶段归内核，技能归角色

阶段归了内核，Skill 还剩什么？答案是：**技能归角色，按产物命名。**

开源版内置 21 份 Skill，没有一份叫"某某阶段"。澄清阶段是一条著述链：`clarify-requirements` 把需求问清，`write-prd`、`write-quality-vision`、`write-tech-design`、`write-dev-plan`、`write-acceptance-criteria` 各产出一份契约文件；实现阶段有 `implement-task` 和 `systematic-debugging`；评测阶段有 `e2e-testing`、`api-testing`、`deterministic-eval` 和修复用的 `fix-from-report`；交付有 `ship-checklist` 和 `sync-overview`；再加上一批通用技能（组件还原、状态结构先行、i18n 抽取等）。

这样命名有个直接好处：**每份 Skill 的产出可验证。** "执行澄清阶段"无法验收，"产出一份带编号的 prd.md"可以。复杂的事靠编排组合，不靠把单份 Skill 写长——平均下来每份不到一百行。

`harness init` 时，Skill 包按角色装进项目：谁在哪个阶段需要哪几份，就在那个角色的任务包里出现。这一点是被上下文压缩逼出来的。长对话里上下文会被周期性压缩成摘要，不同载体的命运完全不同：我测过，靠调用注入上下文的长文档，一次压缩后只剩个位数百分比，第二次压缩后归零。所以流程细节不许只活在对话里——它们要么是磁盘上的文件（Skill、契约、状态），要么是代码里的状态机，对话只负责当下这一步。

Skill 本身怎么写，我的规矩没变：每份只做一件事，步骤化，每一步都要有可验证的产出；还要有至少三条真实踩过的反例。注意，不是"不要写烂代码"这种废话，而是"需求没提错误码时，不许自己编一个"这种能照着执行的具体禁令。

最后，Skill 自己也需要被评测。系统里有一套黄金集（golden set）：`harness skills eval` 拿一批标准任务给 Skill 们打分，分数退化就报警。进化阶段的第一条回路就是它——规则和技能不是写完就供起来，它们和代码一样要回归测试。

## 四、评测必须确定性：不让模型给自己打分

整套系统里我最坚持的一条：**写完代码之后，判断对错尽量用代码，不用模型。**

Anthropic 在他们的长周期 Harness 设计里说得很直白：开箱即用的 Claude 是一个糟糕的 QA。它能看到真正的问题，然后说服自己"这些问题没什么大不了"，照样批准自己的工作。

这不是某个模型的毛病，是位置决定的。让生成者兼任评审者，它天然对自己宽容。所以评测拆成两层：

**第一层，rubric 评测，判"这个功能做对没有"。** 契约的一部分，澄清阶段就写好。条目分两种跑法：command 条目是确定性命令——编译器、grep、测试、五维扫描（见下层），退出码说话；judge 条目确实需要判断的（比如"空状态文案是否说清了下一步"），由评判者凭**新鲜证据**打分——Playwright 现场截图、真实 API 探测的返回，而不是"读一遍代码觉得没问题"。每条检查都必须给证据：具体到哪个文件、哪一行、哪张截图。没有证据，就不算通过。

**第二层，五维扫描，判"这批代码健康不健康"。** 它是独立的一台仪器（`harness scan`，也能脱离全流程单独跑），五个维度：

- 结构：类型能不能编译通过、有没有用忽略规则绕过检查、导入关系合不合架构约束、文件和函数有没有超长；
- 数据：文案键是否齐全、状态结构是否闭合、本地存储的键有没有按命名空间规范；如果项目给了数据规格（Data Spec），逐字段做差异比对；
- 逻辑：需求的功能点清单逐条核对代码里有没有对应的实现和关键分支——这就是为什么功能点必须写在写代码之前，它是评测的考卷，考后出题就没意义了；
- 界面：样式有没有走组件作用域、颜色间距有没有用变量、有没有写死数值；如果给了设计稿，做截图的像素级保真比对；
- 端到端：真的把测试跑起来，统计通过和失败的数量，看主链路有没有覆盖到。

这里有个口径必须说清，否则就是骗人：**扫描有两种模式。** 项目配置齐全时，结构维真的跑 `tsc`、端到端维真的跑你给的测试命令、数据维拿规格逐字段 diff——这是实测。零配置时拿不到这些输入，扫描退回静态检查兜底，这时报告必须明示哪些维度"未实测"，不许拿静态分数冒充真跑的结果。分数的可信度分级，要写在报告里，而不是藏起来。

最后是报告的规矩：每份评测报告写完就不许再改。后续重新生成了代码、重新评测，写新报告，旧的留着。这样复盘的时候能回答一个很关键的问题：这次翻车的原因，上次的报告里是不是已经预警过了？如果预警过，问题在路由和修复；如果没预警，问题在评测本身。没有留档，这笔账永远算不清。

## 五、内核：长流程不能靠模型"记住"

五个阶段如果全在一个主对话里跑，会发生什么？

每进一个阶段，就要把那个阶段的说明加载进上下文。走到后半程，上下文必然触发压缩。而压缩一来，前面阶段的约束和结论就被磨成了摘要里的几句话，越关键的细节丢得越干净。

我用探针式抽查量过这件事：在流程开始时埋一组关键规则作为探针，在每个阶段结束时抽查这些规则还记得多少。主对话模式下，走到第五阶段，信息保留率只剩 40% 左右。

解法是把流程从对话里搬出来，交给一个确定性的内核。它是零依赖的 Node 程序，逻辑很朴素：

每个功能有一份状态文件（`.harness/tasks/<功能>/state.json`），是整条流水线的唯一事实源：当前阶段、各阶段的历史、任务清单、契约文件的位置、评测结论都在里面。**任何人——包括模型自己——都不许手改这个文件**，所有状态变更只能走内核命令。状态文件长这样（简化版）：

```
{
  "feature": "todo-app",
  "phase": "evaluate",
  "history": [
    { "event": "clarify-done", "at": "…" },
    { "event": "task-done", "task": "add-todo", "commit": "a1b2c3d" }
  ],
  "prd": { "source": "imported", "numberingComplete": true },
  "verdict": { "passed": false, "openItems": ["REQ-3"] }
}
```

角色们通过**任务包**和内核打交道：内核按当前阶段生成一份限定输入包——比如评测阶段的评判者只拿到 rubric 和代码入口，开发者的包里根本没有 rubric 这一项。角色跑完，把产出写回文件就退出，下一步做什么由内核读状态决定，不由任何模型"回忆"。

使用上有两种姿势。交互式：你在 Claude Code 或 Codex 里工作，每个功能的第一条命令是 `harness next <功能>`，它只告诉你当前这一步该做什么，做完再问下一步——单步协议，人随时能接管。无人值守：`harness run <功能>` 由驱动器按协议把整条流水线跑完，只在澄清确认和暂停时找人。

评测失败时，内核按结论路由：有开放项，退回实现阶段只修那些项；评判者对 rubric 本身有改进建议，先交规划者回应——这是进化阶段的第二条回路，而且方向被锁死：**rubric 只能收紧，放松必须人批。** 所有循环都有预算上限，耗尽了状态机进入 paused，停下来等人决定，绝不无限打转。

同样用探针式抽查量这个模式，走到第五阶段，信息保留率能到 95% 左右。差别不在模型，在信息放在哪。放在对话里，就要陪着对话一起被压缩；放在文件和程序变量里，就不会。

## 六、踩过的四个坑

**坑一：评测一开始用模型判断。**

最初的评测是让模型看代码、写结论。结果它给自己打了满分，嘴上说 100 分，代码实际跑起来只有三成左右能用，端到端测试全军覆没。

根因就是第四节说的自我宽容。修复是把能确定性化的全部改成命令和证据：编译器退出码、测试通过数、逐行证据。经验一句：Lint 的报错不只是报错，它同时是给模型的修复指令。报告写得越具体，它改得越准。

**坑二：把流程写成文档，让模型照着走。**

早期版本的八个阶段是八份 Skill 文档，靠模型自觉按顺序执行。第一次端到端跑，八个阶段只跑了四个：有几个阶段被莫名其妙地跳过了，流程却显示一切正常。

根因在"下一步走哪"的判断上：靠模型读文档判断，和后来靠代码判断时写错条件，犯的是同一类错误——衔接处没有硬校验。某个阶段还没跑过、历史为空，判断逻辑误判成"已经通过，去下一个"。修复分两步：先把判断拆成明确的三步（先看有没有失败且还有重试次数，再看是不是从没跑过，最后才看通过没有），再往前一步，把整个流程从文档搬进代码状态机。经验一句：这种衔接错误，单元测试测不出来。每个阶段单独测都是对的，错的是阶段之间。它必须端到端真跑一遍才能信。

**坑三：在主对话里跑完整条流水线。**

症状就是第五节的前半段：跑到后半程，前面阶段立的规矩基本被压缩吃掉，后面的阶段等于在一个失忆的上下文里凭感觉干活。

修复是把阶段拆给独立角色、状态搬进文件。经验一句：主上下文永远不要堆叠流程内容。任何"在一次长对话里跑完长流程"的设计，都会在中段崩掉，只是早晚问题。

**坑四：静态分数冒充实测分数。**

扫描器早期有个很隐蔽的问题：零配置跑出来的静态检查分数，和配置齐全后真跑编译、真跑测试的分数，长得一模一样——都是一个 0 到 100 的数字。拿前者去汇报，等于说"我测过了"，其实最关键的几个维度根本没测。

修复是给每个维度标来源：实测还是静态推断；拿不到输入的维度在报告里明示"未验证"，分数旁注明口径。经验一句：**测不成，就写无法评估，不许写成一个看起来很真的数字。** 这条对评测系统是诚信问题，不是精度问题。

## 七、落地：现在只需要三步

这套系统已经开源，所以"落地"不再是从零自建，而是三步：

1. **装**：`git clone` 仓库，或把一句话 prompt 粘进你正在用的 Claude Code / Codex，让 Agent 自己装好 CLI 并初始化你的项目——我在[体检页](https://maoxunxing.com/ai/ai-code-health-check/)上放了一个现成的"一个 prompt"版本，复制即用。
2. **跑**：`harness init` 按你的技术栈（Next.js / React / Vue / Node）装好规则和技能包；然后 `harness new <功能>` 开第一个功能，有成稿 PRD 就加 `--prd` 导入。交互式用 `harness next` 一步步走，无人值守用 `harness run`。
3. **先体检，再上全流程**：拿不准值不值得上整套，先对现有仓库跑一次 `harness scan` 五维体检，或者在上面的体检页粘贴公开仓库链接在线跑一份——十分钟拿到一份带证据的报告，再决定。

如果你想抄的是设计而不是工具，我的建议仍然是先拿走最小的一块：**语言层加工程层约束。** 严格模式加两个 Lint，今天下午就能让 AI 在你的项目里少犯一类错。约束不需要等系统完整才生效，这是四周路径也好、三步也好，都不变的第一步。

至于建设顺序，我自己的经验是：先钉约束（一周），再给澄清和实现写技能，再上评测，最后才值得写内核。顺序反过来——先搭编排、后补评测——是最常见的死法：流程跑得越顺，垃圾产出得越快。

## 八、局限：它测不了什么，我很清楚

**第一，美学层只能测一半。**

自动化能查的是：有没有用变量、作用域对不对、截图和设计稿的像素差多少。但"颜色搭配合不合理""间距有没有节奏""字号层次清不清楚"，这些判断目前自动化只能覆盖一半左右，剩下一半还得靠截图加人工评审，或者靠一个独立的评审代理打分，而且那个分数要刻意往怀疑的方向校准，不能再犯自我宽容的毛病。

这也是为什么我说美学是前端特有的一层，同时它也是五层里最弱的一层。承认它弱，比假装它被解决了重要。

**第二，"通用"还没有完全验证完。**

这套系统在 Next.js 项目上验证得最深；Vue 等其他栈的栈包已经就位，但我的验收线是：Next.js 与 Vue 两个异构项目各用它跑通一个真实需求，在那之前我不对外宣称"通用已验证"。工具可以先用，结论不能先行。

**第三，约束有保质期。**

这套系统不是搭完就一劳永逸的。每次模型升级，都应该做一次消融：把某条约束撤掉，看效果变好还是变差。有些约束是补模型当下的短板，模型补上了，它就从护栏变成了路障；还有个更隐蔽的现象，模型会过拟合它长期使用的工具和 Harness，换掉某个环节的做法，效果反而会掉，这也只能靠实测发现，靠想是想不出来的。

还值得一提的是整个行业的背景并不乐观：有调查说，高频使用 AI 编码的人里，接近七成报告 AI 生成的代码至少有一半概率带来部署问题，一半左右的人觉得代码质量在下降。速度先到了，交付系统没跟上。这套 Harness 解决的是我自己项目里的那一份，不是什么通用解药。

## 写在最后

回到开头那句话：不要更聪明的马，要更好的赛道。

模型会变，而且变得很快。但回头看，这套系统里真正的核心不是哪个具体的数字或者工具，而是五个补偿性的设计：先定义完成再动手、检测和修复分开、上下文尽量被动给到、长流程拆进独立上下文、评测只信确定性的证据。

它们补偿的不是模型的智商，而是模型的几个结构性短板：不知道自己不知道、会说服自己没问题、记不住长流程、会被上下文淹没。这些短板短期内不会因为模型大一号就消失，所以这套设计也不会很快过期。过期的只会是具体的某条约束，那正是消融要定期清理的。

这套系统已经完整开源：[frontend-harness-cli](https://github.com/XingMXTeam/frontend-harness-cli)（内核、三个角色、21 份 Skill、五维扫描都在里面，扫描的前身是早期的 ai-code-gate，现已并入作为传感器层）。只想先看一份报告的，去[体检页](https://maoxunxing.com/ai/ai-code-health-check/)粘贴一个公开仓库链接就行；想直接让自己的 Agent 用上它，同一个页面有一条复制即用的 prompt。

上篇讲为什么需要现场，这篇讲现场怎么搭。下一篇如果写，我想写写进化回路：一个系统怎么把每次失败变成自己的规则——哪些已经自动化了，哪些还必须留给人。
